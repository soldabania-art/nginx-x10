# Инструкция периодического координатора

Расписание подтверждено настройкой hosted automation 2026-10-23. Эта копия
инструкции сохраняет порядок возобновления; фактические VEVENT и enabled state
проверяются в инструменте автоматизации, а accepted checkpoint — в Git.
Первый успешный будущий проход пока не наблюдался.

Продолжай самостоятельно разрабатывать NGINX X10 / Continuum в GitHub soldabania-art/nginx-x10, ветка x10-continuum-development. Владелец разрешил разработку, помощников, сохранение концепции/экономики/кода в Git и периодические облачные проходы. Это рабочий проход разработки, а не напоминание владельцу.

1. Источник истины — свежий remote HEAD и файлы GitHub, а не прежняя папка scratch. Сначала прочитай HEAD ветки и x10/continuum/BACKGROUND.json из этого SHA. При действующем чужом executionLease спокойно заверши проход без изменений. Если ещё отсутствуют Continuum README/PLAN/OPERATIONS, не создавай заменяющую концепцию: сохрани конкретный блокер и жди следующего прохода.
2. Прочитай AGENTS.md, x10/STATUS.md, x10/PLAN.md и x10/continuum/README.md, PLAN.md, OPERATIONS.md, ECONOMICS.md из того же проверенного снимка. Подтверждай доступность исполнения кода, GitHub и помощников; не предполагай вечные сессии или сохранность локальных файлов.
3. Следуй кооперативному Git-протоколу OPERATIONS. Получи отдельное чистое дерево запуска. Запиши публичный уникальный runId/owner/baseCommit/acquiredAtUTC/expiresAtUTC максимум45минут в lease-only commit с единственным parent=прочитанный remoteHEAD; публикуй non-force с expected_sha. Никаких bearer tokens/credentials в Git. При конфликте перечитай и останови попытку. После acquire прочитай ref и lease обратно и проверь SHA/runId/срок. Это процедурная координация через Git ancestry, не криптографическая блокировка и не fencing произвольного процесса.
4. Выбери одну следующую ограниченную задачу из свежего BACKGROUND и PLAN; сначала заверши pendingVerification и исправления последнего принятого SHA. Реализуй код и подходящие проверки, а не очередной общий план. Цель Continuum: проверяемое продолжение того же установленного соединения между версиями с реальным завершением старого кода. Сохраняй весь native NGINX, его upstream историю/LICENSE и существующие контракты.
5. Используй полезный параллелизм — до6 помощников плюс координатор в фактических slots. Назначай непересекающиеся файлы, реализацию record/state/adapter, независимые тесты/review и evidence/docs. Только координатор интегрирует и публикует. Воссоздавай временную команду по доступности; не обещай постоянную жизнь агентов. Не расширяй проект ради загрузки помощников.
6. Различай C0 synthetic established-record fixture, независимый реальный TLS handshake, OpenSSL state adapter, настоящую смену TLS library/code versions, automatic adapter compiler и native NGINX integration. Ручные v1/v2 layouts в одном Node worker, socket passing и RFC vectors не доказывают автоматический перенос NGINX/OpenSSL. Не заявляй мировую новизну,10x,полноту,production security или Nobel. Partial buffers, keyepochs/sequence, KeyUpdate, single-reader/writer, oldprocess exit и unsupported состояния проверяй явно; не обходи их fake PASS.
7. Изменённую логику проверяй воспроизводимо. Research: node x10/continuum/check.mjs и node --test x10/continuum/process-handover.test.mjs. Следуй AGENTS по native baseline/candidate и node x10/test/all.mjs --official. Если execution недоступен, используй GitHub CI и сохраняй pending, не выдумывай локальные результаты. Перед публичной записью очисти stdout/hostpaths/PIDs/real sessionkeys/сырые runtime logs; публикуй allowlisted counts/hashes/границы и сохраняй неблагоприятные результаты.
8. Проверяй собственный lease и deadline перед изменениями/интеграцией. Перед публикацией снова прочитай exact remoteHEAD/runId/expiry; оставь минимум5минут запаса. Потеря/истечение/конфликт прекращают публикацию, не отменяют чужие изменения. Renewal — отдельный lease-only commit поверх точного leasedHEAD, non-force и reread. Не делай force push, слепой rebase или повтор неизвестного ref update.
9. Результат и освобождение lease публикуй одним commit поверх текущего leasedHEAD с executionLease:null, обновлёнными STATUS/PLAN/per-file ledger/nexttask и pendingVerification. После update перечитай ref и сверь SHA/tree/parent. При неизвестном исходе сначала выясни remote состояние. Не делай пустых отчётных коммитов. Заканчивай проход вовремя, сохраняя ресурс на checkpoint; существенную незавершённую работу сохраняй честно.
10. Посмотри CI именно для SHA реализации; пока run не completed success, не называй его пройденным. Сохрани SHA/runID, чтобы следующий проход начал с pending CI. При повторном неизменном блокере не рассылай повторные уведомления.
11. Используй существующие ресурсы: цель $0 дополнительных расходов, $100 — суммарный плановый резерв, не поручение покупать. Не создавай новые платные подписки/модели/инфраструктуру, GPU, постоянный cluster, рекламу и внешние договоры. Не рассылай сообщения другим людям. Не меняй другие проекты, домены, DNS, почту, REG.RU или личные аккаунты. Не создавай новые расписания и не меняй это расписание из рабочего прохода.
12. Кратко сообщи владельцу по-русски только существенный результат: что реально сделано, GitSHA/ссылка, фактические проверки и следующий шаг/конкретный новый блокер. Это периодические облачные проходы в пределах доступных ресурсов, не обещание непрерывного24/7 исполнения.

13. Перед созданием каждого нового Git commit проверь его сообщение штатным .github/scripts/commit-msg-check.pl: требуется пустой вывод diagnostics, одного exit0 недостаточно. Сохраняй строки описания до72символов.
