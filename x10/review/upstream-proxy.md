## Architectural conclusion

Keep original NGINX as the network core. The Node ENGINE X10 prototype is a laboratory for management contracts and failure experiments, not a replacement for NGINX's protocol engines. This source already contains smooth weighted round robin, weighted least connections, random/two-choice, key/consistent/IP hashing, least-time with inflight accounting, sticky sessions, upstream zones, runtime DNS/SRV updates, connection reuse and a disk cache. Those are existing capabilities to preserve, not new features to claim.

## Balancer invariants and current features

1. **Smooth weighted RR is stateful, not simple index rotation.** Eligible peers accumulate `current_weight += effective_weight`; the best loses the accumulated total. Failed attempts reduce effective weight by configured weight divided by `max_fails`, clamp at zero, and gradually recover effective weight on later eligible selections. Selection excludes tried, down, temporarily failed and saturated peers. A dedicated single-peer path deliberately does not apply the same passive failure suppression; it still checks down and `max_conns`.
2. **Acquire/free symmetry matters.** Successful selection increments peer connections and, with zones, references. Every failure, retry, cancellation and finalization must decrement/unreference exactly once. Shared removed peers can be zombies until their active references disappear. An optimization must preserve these ownership rules.
3. **Peer identity is configuration-sensitive.** Per-request generation guards prevent selection using a stale tried bitmap after dynamic membership changes. Zone DNS/SRV updates maintain primary/backup priority, weights, totals, counts and tries. Non-NXDOMAIN resolver failures retain the current membership and retry; NXDOMAIN can remove it. Reload pre-resolution can reuse old resolved addresses.
4. **Connection limits and idle caching differ.** `max_conns` is a peer's active connection counter; keepalive cache size is an idle-cache bound. The cache is process-local, so neither cache size nor active counter alone is a machine-wide total socket budget. Zones affect which peer counters are shared; idle cache entries remain a separate resource.
5. **The source has advanced algorithms already.** Least connections uses weighted cross multiplication and RR ties. Random uses weighted ranges; two-choice compares weighted connections. Hash supports Cache::Memcached compatibility and a consistent ring with 160 points per unit of weight. IP hash uses the first three IPv4 bytes or all IPv6 bytes. Hash/random strategies have bounded selection attempts before fallback. Least time uses 5% new/95% previous rounded EMA, header/last-byte mode, optional inflight measurements, 20ms clusters, a five-second cap and aging that gives slow peers another chance. These semantics need tests before any tuning.
6. **Sticky is native in this pinned source.** Cookie, route and learned session modes preserve original callbacks. Learned sessions use shared lookup and expiry trees, default ten-minute timeout and a designated expiry worker. SID hints also affect balancer eligibility and draining semantics; do not remove SID/generation checks when optimizing selection.

## Keepalive invariants

`ngx_http_upstream_get_keepalive_peer` invokes the original balancer before looking for a cached connection. A cache hit must match the selected socket address and, with local mode, the upstream configuration tag. Valid reuse requires a completed request body, protocol-confirmed `u->keepalive`, no read/write failure/EOF/timeout, remaining request-count and connection-age budget, and a worker that is not terminating. Idle-ready sockets are checked with a one-byte `MSG_PEEK`; unexpected readable data leads to closure.

In this source explicit upstream groups receive a default local cache of 32 entries when `keepalive` was not explicitly configured. Defaults read in code are 60 seconds idle timeout, one hour total age, and 1000 requests per connection. `keepalive 0` disables the cache. SSL session storage and asynchronous TLS closure are separate from socket reuse and must remain compatible with peer wrappers.

## Retry and response-commit invariants

`ngx_http_upstream_test_next` handles configured status-based retry before a response is committed. `ngx_http_upstream_next` handles transport/timeout/invalid-header failures and frees the old peer with the correct state. HTTP 403/404 use `NGX_PEER_NEXT`, not passive-failure penalization. Cached-socket transport failure has special tries accounting.

After a request is marked sent, POST, LOCK and PATCH require the explicit `NON_IDEMPOTENT` retry bit. A sent unbuffered request body cannot be replayed. Retry count, failure mask and the total next-upstream timeout must all allow another attempt. This is a transport policy, not a proof of application-level exactly-once execution; the control plane must never silently broaden retry masks. Once response headers/body are committed, errors are finalized/flushed/closed rather than replacing already-sent data with a new status.

Response `Content-Length` duplicates are rejected. `Content-Length` together with `Transfer-Encoding` is rejected regardless of arrival order, and accepted response transfer coding is exactly chunked. The prototype's previously fixed framing-smuggling regression is a useful differential fixture, not evidence of a bug in original NGINX.

## Buffering, disk cache and streaming invariants

Request buffering and response buffering are independent. Buffered request chains can be rewound, including file positions, when retry policy permits. Unbuffered request flow advances through the output chain with explicit blocked/read/write event state. Response buffering uses `ngx_event_pipe` with configured memory buffers, busy buffers, rate limit, temporary file size/write bounds and read/send timeouts. The event-pipe implementation itself belongs to another source-review manifest and must be included in final system conclusions.

Nonbuffered responses maintain free/busy/output chains and send flushes without waiting for the whole body. Read progression respects downstream backpressure. Upgraded connections have distinct bidirectional buffers, timeouts, client-abort and EOF completion paths. `X-Accel-Buffering` may change response buffering only when configured to permit it. Therefore an AI/SSE preset should choose existing buffering and timeout controls explicitly; it must not globally disable buffering or disk caching.

Cache details already present:

- Shared slab/rbtree metadata and an inactivity queue; disk filenames use the cache key digest. File reads additionally verify CRC32, full original key, format version and header bounds, so digest replacement is not a drop-in optimization.
- Vary-derived variants include normalized request-header values. `Vary: *`, oversized Vary, Set-Cookie and cache-control exclusions can prevent storage. Cache-bypass, no-cache predicates, method rules and range restrictions are distinct decisions.
- Lock age and lock timeout coalesce misses; waiters use event timers bounded by 500ms steps, not a blocking worker sleep. Stale-while-revalidate, stale-if-error, background refresh and 304 header updates already exist.
- Only a complete, length-consistent response should become a cache/store file. Cache update renames a temporary file, then updates shared metadata; revalidation checks inode/length/header identity before rewriting metadata.
- Cache loader/manager have file-count, elapsed-time and sleep budgets, maximum size and optional free-space floor. Deletion releases the shared mutex for filesystem work while retaining node count/deleting guards. Long-locked entries are moved instead of blindly freed; cleanup clears updating ownership only for the matching lock generation.

## HTTP/1 proxy adapter

Entry points are `ngx_http_proxy_handler` at `src/http/modules/ngx_http_proxy_module.c:876`, `ngx_http_proxy_create_request:1184`, `ngx_http_proxy_body_output_filter:1638`, `ngx_http_proxy_process_header:1892`, `ngx_http_proxy_input_filter_init:2070` and `ngx_http_proxy_merge_loc_conf:3668`.

The proxy adapter builds an HTTP request from compiled complex values and headers. It preserves the original unparsed URI where valid, otherwise combines the configured URI/location replacement, escaping and query arguments. Dynamic `proxy_pass` has a different compiled-value path; URI parts in named/regex and certain conditional locations are rejected during configuration. These distinctions are compatibility requirements for any configuration generator.

Body framing is generated from internal body length/chunk state, rather than forwarding arbitrary client transfer framing. The default header table suppresses hop-specific fields and generates Host, Content-Length and Transfer-Encoding through the adapter. An unbuffered chunked upload requires a suitable upstream HTTP version. The body output filter writes chunk sizes, data and a terminating zero chunk while retaining chain ownership until the writer consumes buffers. Buffered requests copy buffer descriptors, preserving body bytes and file positions for the common retry machinery.

The response path distinguishes fixed-length, chunked, close-delimited and bodyless responses. HEAD, 204 and 304 terminate according to their rules. Chunk parsing and optional trailers are incremental, with a configured header-buffer bound. An incomplete body or extra bytes at a purported message boundary must prevent unsafe connection reuse. Upgrade requires the matching client upgrade request. HTTP/0.9 status-line fallback is existing compatibility behavior; changing it globally would be a behavior change, not a neutral cleanup. Location/Refresh rewrites, cookie domain/path/flags rules, custom methods/body, error interception, store/cache, request and response buffering, range controls and rate limits must survive a fork.

Important defaults in this exact commit: `proxy_http_version` merges to **1.1**, and its parser also accepts **2** when built with HTTP/2 support. Request/response buffering default on; connect/send/read timeout defaults are 60 seconds; response buffers default to eight page-sized buffers; the default temporary-file maximum is 1GiB. Merge code validates buffer relationships instead of accepting internally inconsistent sizes. Cache storage, lock, background refresh and revalidation are opt-in. Upstream SSL session reuse defaults on, while SNI and certificate verification default off; enabling verification requires a trust file. A secure deployment preset may enable verification/SNI explicitly while preserving existing configuration semantics.

## HTTP/2 upstream proxy and gRPC

`proxy_http_version 2` dispatches to `ngx_http_proxy_v2_handler` (`ngx_http_proxy_v2_module.c:216`). That adapter retains proxy configuration, cache-key, redirect and cookie-rewrite integration, and supports both buffered and nonbuffered responses. The request encoder is at `:320`, request DATA output at `:1063`, response header processing at `:1429`, frame/body processing at `:2124`, frame parsing at `:2478`, HPACK fragment parsing at `:2793`, and connection-state attachment at `:4206`.

gRPC installs its callbacks at `ngx_http_grpc_handler` (`ngx_http_grpc_module.c:564`), uses `create_request:734`, `body_output_filter:1351`, `process_header:1716`, `parse_frame:2655`, `parse_fragment:2970`, and `get_connection_data:4376`. It explicitly chooses unbuffered request and response handling, passes trailers and early hints, and preserves output needed for bidirectional flow. `TE` is generated as `trailers` when supported by the incoming request. `grpc://`, `grpcs://`, variable targets, native TLS/SNI/verification/client certificates and ALPN `h2` exist. A gRPC application status carried in trailers is not treated by these files as a new generic automatic retry policy.

Both HTTP/2 adapters implement a client transport with:

- A connection preface, SETTINGS, disabled server push, a zero dynamic HPACK table, static-name/index support and Huffman decoding. Decoded name/value totals are charged against the configured response-header budget; invalid name/value characters and invalid indexes fail parsing.
- HEADERS/CONTINUATION sequencing, explicit END_HEADERS/END_STREAM handling, padding checks, bounded accepted frame size, Content-Length accounting and trailer parsing. Body bytes remain buffer-chain slices; control bytes are separated from payload bytes.
- Separate stream and connection send/receive windows. DATA output is limited by both windows; WINDOW_UPDATE and SETTINGS can resume blocked output. Zero/overflowing window updates and excessive initial window sizes are rejected. PING/SETTINGS ACK output uses reusable control buffers; excessive queued control-frame creation has a guard.
- GOAWAY/RST processing that influences completion/reuse. A GOAWAY last-stream ID below the current request fails the attempt; a last ID that includes the current request permits completion but prevents another request on that connection. Both implementations contain a TODO for a more precise non-idempotent retry decision; that TODO is not authorization to replay a request.

**This is sequential HTTP/2 keepalive reuse, not concurrent multiplexing of unrelated upstream requests.** Each leased connection has one active request context; unrelated nonzero stream IDs are rejected. A cached connection preserves initial/send/receive-window data in connection-pool cleanup storage, and the next request increments its odd stream ID by two. `u->keepalive` is granted only after response/control completion, output closure, a clean frame boundary and no GOAWAY. This source observation distinguishes upstream transport from the separate downstream HTTP/2 server engine.

Concurrent upstream HTTP/2 multiplexing is a possible research branch, not an established improvement. It would require connection ownership independent of a single request pool; stream scheduling, per-stream cancellation/error isolation, GOAWAY unprocessed-stream accounting, shared-window fairness, buffer/memory bounds, TLS/configuration isolation, and revised peer `conns`/`max_conns` semantics. Measure handshake/socket savings and tail latency under real concurrency before accepting that complexity. The current transport remains the default and compatibility baseline.

FastCGI/SCGI/uWSGI normalize passed HTTP header names to `HTTP_...`, avoid duplicating configured params, and join duplicate values with comma-space except Cookie's semicolon-space. Generated script lengths are checked during serialization. Replacing these adapters with generic HTTP forwarding loses their wire protocols and application compatibility.

FastCGI additionally recycles a large pre-header STDERR buffer to avoid accumulating PHP warning output; its cache path repairs the record-header representation for that case. Content-Length shortfall is an error, and excess data stops/truncates according to filter rules. `fastcgi_keep_conn` defaults off; when enabled, clean END_REQUEST completion and padding/message boundary are required for idle reuse. These are separate from merely setting a TCP keepalive option. SCGI/uWSGI do not set a protocol `u->keepalive` completion flag in these adapters, so a shared balancer cache alone does not imply persistent reuse for them.

## Concrete regression and experiment gates

Use the pinned, unmodified binary as the baseline, with identical compiler, optimization flags, modules, OpenSSL/library versions, CPU affinity, worker count, OS limits, backend behavior and workload. Record configuration and command lines with every result. Compare throughput at equal error rate, p50/p95/p99 latency, CPU time per request, RSS, open sockets, TLS handshakes, disk reads/writes, cache hit/stale state, bytes delivered and application side effects. A throughput gain that duplicates writes, changes cache visibility, shifts errors or expands memory is a failure.
