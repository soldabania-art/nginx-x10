# NGINX core structures: source reading notes

Source: official NGINX repository, commit `148c75678cd4171338c31d4ed4c02411736d5fe9`, version 1.31.9. This is a supplemental reading assignment; exact per-file evidence is in `core-structures-coverage.json`. All 39 assigned files (8,964 lines) were read in full. No file is counted as partial, structural-only or unread. No source or product changes are made.

## BPF, CPU, checksums and password format compatibility

- `ngx_bpf.c/h`: thin Linux BPF syscall wrappers load programs, relocate a map symbol into instruction operands and create/access maps. Kernel support, privileges and verifier acceptance remain external requirements. The optional verifier log is bounded to 32 KiB.
- `ngx_cpuinfo.c`: x86 CPUID vendor/family/model heuristics choose a cache line size, with a no-op implementation for other build targets. Historical optimization comments are not a current comparative benchmark.
- `ngx_crc.h`, `ngx_crc32.c/h`: rotate/sum legacy checksum plus CRC32 and CRC32c lookup helpers, with incremental init/update/final conventions. CRC output compatibility matters; none provides cryptographic authentication. The short table is cache-line aligned at initialization.
- `ngx_crypt.c/h`: dispatches `$apr1$`, `{PLAIN}`, `{SSHA}` and `{SHA}` formats, falling back to platform crypt. APR1 uses compatibility MD5 crypt with 1,000 rounds; SHA variants use SHA-1 and SSHA appends salt. PLAIN preserves a clear password behind a prefix. These are compatibility formats, not recommendations for new password storage. Preserve verification semantics; do not create a custom cryptographic replacement.

## Structured data and digest primitives

- `ngx_data.c/h`: pool-owned tagged object/list/string/integer/boolean/null tree, linked append cursor, declarative handler tables, optional field selection and decline sentinel. Structure-offset handlers copy string bytes into the destination pool; UTC time formatter preserves optional milliseconds. Callers must supply valid type/offset declarations and keep parent/child pool lifetimes coherent.
- `ngx_md5.c/h`, `ngx_sha1.c/h`: incremental block hashing (64-byte buffers), explicit byte-order encoding, digest finalization and context clearing. These implement existing protocol/format compatibility; their presence does not make MD5/SHA-1 appropriate for new collision-resistant signatures or password storage. Preserve bytes, partial-block behavior and endianness across builds; use published vectors and boundary tests for any maintenance.
- `ngx_murmurhash.c/h`: deterministic seed-zero MurmurHash2, used for partitioning/selection rather than authentication. Changes alter assignment stability.
- `ngx_siphash.c/h`: keyed SipHash-2-4, two compression rounds per block and four final rounds. A hash-table/keyed-hash primitive is not a password KDF or a replacement for TLS. Full blocks use an eight-byte `memcpy`, while the tail is assembled explicitly; cross-endian portability requires vectors on supported targets before changes. No custom cryptography is proposed.

## Radix and red-black trees

- `ngx_radix_tree.c/h`: IPv4/IPv6 bitwise prefix lookup remembers the last non-sentinel value, so it implements longest-prefix match. Duplicate values at the same prefix return BUSY. Deletion prunes valueless leaf ancestry into a reusable free list; storage is pool-owned and page-aligned. Default shallow preallocation depends on nodes per page. Prefix masks, sentinel `NO_VALUE` and root handling are caller/API invariants; validate empty/default/exact/overlapping prefixes before altering traversal.
- `ngx_rbtree.c/h`: intrusive red-black insertion/deletion/rotations, sentinel-black invariants, callback-specific insertion ordering and in-order successor. A separate timer comparator subtracts keys with signed interpretation to tolerate short-range millisecond wraparound. Keys alone need not be unique: caller-specific comparators may handle collisions. Tree code supplies no internal synchronization, so shared users must keep their established external locks.

## Shared-memory locks and slabs

- `ngx_rwlock.c/h`: atomic reader count or all-ones writer marker, compare-and-swap acquisition, exponential CPU pause followed by scheduler yield, writer-to-reader downgrade. No explicit writer-waiting queue/fairness policy is present; sustained readers must be measured before any starvation/fairness claim. Upstream-zone builds require atomic operations.
- `ngx_shmtx.c/h`: shared lock owns the worker PID, spins then optionally waits through a process-shared semaphore; wakeup carefully consumes a waiter count. Unlock compares owner PID; forced unlock takes an explicit PID. Non-atomic builds use file locks on an unlinked lock file. Changes must preserve crash-owner recovery integration, semaphore interruption handling and build fallbacks. This is synchronization within shared memory on a host, not a distributed lock.
- `ngx_spinlock.c`: generic atomic value lock, exponential pause and scheduler yield; threaded builds require supported atomics.
- `ngx_slab.c/h`: power-of-two size classes up to half a page, then contiguous whole pages. SMALL bitmap lives inside the data page; EXACT bitmap occupies the page descriptor; BIG combines shift and allocation bits. Descriptor low pointer bits carry page type. Free runs split on allocation and coalesce with both neighbors; first/continuation markers and `pfree` must remain consistent. Full/partial size-class lists, `total/used/reqs/fails` counters and reserved bitmap chunks are accounting invariants.
- Slab `alloc/calloc/free` wrappers acquire the shared mutex. Their `_locked` variants require the caller already to hold it, enabling atomic compound tree/zone updates without recursively taking the lock. Do not substitute ordinary per-process heap allocation for shared data, or remove these locks on the basis of single-worker measurements. All shared pointers depend on the established mapping/lifetime contract. Failed allocations return NULL; invalid/double/wrong-chunk frees are logged. Debug builds can poison allocation/free areas.

## Paths, temporary files and copy/rename

- `ngx_file.c/h`: platform-specific absolute path recognition, path prefixing, hashed directory layouts, atomic sequence-based temp names and collision jumps. Temp opens install pool cleanup that either deletes or closes according to `clean/persistent`; preserve cleanup ownership when asynchronous thread writes use the same file object. Hash levels and same-path ownership conflicts are checked during configuration. Directory creation sets owner access and may chown/chmod for the worker user.
- Extended rename applies requested mode/time, optionally creates destination parents, handles platform replacement behavior and cross-filesystem EXDEV by copying to a destination-side temporary name, renaming it, then deleting the source. This path is not a single cross-filesystem atomic transaction or a durability/fsync guarantee. The copy helper defaults to a 64 KiB buffer, records source metadata when unspecified, rejects short reads/writes, closes both fds and frees its buffer on all exit paths.
- Tree walking skips dot entries, dispatches regular files/directories/special entries through callbacks, supports pre-directory decline, and restores per-level context on exit. ABORT propagates fatal conditions. Any new temp/copy optimization needs descriptor/leak, cancellation, permission, disk-full, EXDEV and cleanup tests, not only throughput tests.

## Open file cache: descriptor, symlink and event invariants

- `ngx_open_file_cache.c/h` caches open descriptors and metadata, directory metadata and, when enabled, lookup errors. Names are indexed by CRC32 plus full-name comparison, so checksum collisions do not alias paths. An LRU-style queue tracks inactivity; maximum capacity forces one eviction and can remove a further one or two inactive entries. `valid` controls ordinary revalidation and `min_uses` controls retaining open fds. Error caching and stale intervals affect observable behavior; preserve configured semantics.
- Every request borrows a referenced descriptor through pool cleanup. If a path is replaced while an old file is in use, the old entry leaves the lookup tree and is marked `close`, while users keep the old fd until its count reaches zero. A new entry represents the new file. Eviction/cleanup must never close a live borrower or free an event still referenced by a callback. Cache-pool cleanup cancels events and drains entries before memory teardown.
- Vnode notifications are optional. Event installation failures fall back to time-based retests. A newly installed event is trusted only after one further revalidation because the file might have been removed between open and registration. Event removal handles active borrowers and the one-shot callback frees its own event data only after all cache/file use is finished. Do not simplify away that race protection.
- Ordinary reads open nonblocking to avoid blocking on FIFO/special paths; append-log opens use different flags. Existing-fd identity is checked with the file unique identifier. Read-ahead is conditional on configured size and files over 128 KiB. `O_DIRECT`/platform direct-I/O activation follows the configured file-size threshold and records `is_directio` only after success. Cached descriptor direct-I/O state is reused, so downstream aligned-I/O handling must remain coordinated; a new cache policy cannot assume each borrow has an independent fd flag state.
- With OPENAT support, symlink policy walks components via directory fds, with NOFOLLOW or same-owner verification. Same-owner mode compares the opened fd owner with `fstatat(AT_SYMLINK_NOFOLLOW)` even if the latter sees a regular component, explicitly accounting for replacement races. The `from` prefix skips policy checks on the accepted prefix by design; cache reuse checks both symlink policy and prefix. Trailing slashes reopen `.` to enforce directory semantics. Platform O_PATH/fstatat fallbacks and all intermediate-fd cleanup must survive maintenance.
- No new file-cache performance or security claim follows from source reading. A candidate improvement is better observability of hit/revalidation/error/eviction reasons or measurable reduction in pathname syscalls, gated by atomic replacement, unlink/open, symlink ownership race, FIFO, permissions, direct-I/O, log rotation, descriptor-pressure and reload/cancellation tests. Preserve correctness before measuring system-call savings.

## JSON grammar and output

- `ngx_json.c/h`: tagged-data serialization performs a sizing pass with overflow checks before pool-buffer allocation, then an encoding pass with JSON name/string escaping. Integer and boolean sizing deliberately reserves a maximum and actual buffer length follows the encoder cursor. Tags/child links are trusted internal data; maintain object/list ordering, integer bytes, escaping and NULL behavior.
- `ngx_json_parse.c/h`: callback grammar machine recognizes objects, arrays, keys, string/number/boolean/null scalars; checks separators, number grammar, escapes and valid UTF-16 surrogate pairs. Container stack is allocated lazily, maximum depth defaults to 64. Callback SKIP suppresses emissions but continues syntax validation; exact skip scope differs for keys, container-open and array-element values. Callback error results propagate. Tokens are raw slices of the supplied bytes, with separate escaped-token event types, so consumers must decode/copy before extending input lifetime. Numeric tokens are not converted by the parser, avoiding an implicit floating-point precision policy.
- Do not infer arbitrary network-chunk streaming from the `ctx` API name: token-start pointers are local to a call and a bare top-level number is finalized at that call's end. Callers' actual buffer/completion contract must be checked before reusing this as an incremental transport parser. The parser validates escape sequences but does not independently validate unescaped UTF-8 byte sequences; consumers must keep any UTF-8 requirements explicit. Duplicate-name policy belongs to the consuming callback. These are source observations, not demonstrated vulnerabilities.
- `ngx_json_unescape.c/h`: unquoted string bodies decode into a caller-owned destination whose capacity must be at least source length. Normal escapes, BMP values and paired UTF-16 surrogates are supported; control bytes, invalid/truncated escapes and unpaired surrogates fail. Decoding never requires a larger buffer than the escaped input; decoded length replaces capacity on success. Raw unescaped bytes are copied, so this helper also is not a full UTF-8 validator.

## Preservation and measurable improvement paths

| Area | Compatibility and correctness to preserve | Candidate measurement before any claim |
| --- | --- | --- |
| Hash/digest primitives | Published vectors, zero/partial/multiple blocks, byte order, partition stability, final context clearing | Cycles per byte by input size and target architecture; never substitute algorithms without an explicit compatibility boundary |
| Radix/tree indexes | Longest-prefix result, duplicate and delete behavior, sentinel/color/parent links, timer wrap comparator, external locks | Lookup/update distributions, memory per prefix, cache misses; include IPv4/IPv6 and adversarial key distributions |
| Slab/locks | Pool geometry, bitmap metadata, whole-run coalescing, shared pointers, lock ownership, `_locked` calling contracts | Contention and tail latency across worker counts, size classes, fragmentation, allocation failure counters; include process exit/reload |
| Paths and file cache | Path/symlink policy, fd references, old/new inode separation, cleanup/event lifetimes, direct-I/O state, error-cache validity | Syscalls/request, fd high-water mark, revalidation reasons, cold/warm latency; correctness under rename/unlink/rotation/permissions/failure |
| JSON/data | Stable encoding, escaping, overflow checks, depth/skip rules, token lifetime, caller completion contract | Allocations, bytes copied, throughput and tail latency at depth/size boundaries; corpus and sanitizer/fuzz validation before parser changes |
| BPF/CPU platform hooks | Kernel verifier and architecture/build feature checks, syscall errors, non-supported fallback behavior | Startup/failure diagnostic quality and actual workload CPU/cache behavior on supported kernels/architectures |

These are improvement hypotheses, not achieved results. First add reproducible correctness and diagnostic evidence around the existing native behavior, then benchmark one isolated change against this exact pinned source with identical build flags, workload, logging and hardware. No 10× throughput, reliability or security conclusion is established by reading. New security requirements should use maintained standard protocol/cryptographic libraries and migration policies rather than a custom cryptographic design.
